執行紀錄

資料庫狀態

GCP 專案 ID 與資料來源模式（native / external / materialized）：這一組設定同時影響 最新戰報、持股燈號、個股分析、回測研究、因子相關性掃描、因子回歸模型全部功能實際 從哪裡讀資料，是選用的進階功能，不設定的話維持讀 Drive 月份檔案（native 行為）。
external（即時讀取）：不用先匯入，執行任何一項查詢前都會自動把 BigQuery 外部資料表 重新指向歷史資料夾裡「目前所有」CSV 檔案，Apps Script 完全不會讀取檔案內容。 缺點：每次查詢都要即時讀 Drive，比較慢；且用「欄位順序」對應 schema， 如果 Drive 上 CSV 的實際欄位順序跟系統不一樣，資料會整個對錯欄卻不會報錯。
materialized（推薦）：一樣不用匯入，但改用「欄位名稱」對應（BigQuery 自動辨識 CSV 標題列文字當欄名，不管來源檔案欄位順序如何都不影響，對不上名字會直接報錯，不會靜默算錯）。 執行查詢前只有「超過設定的重新整理間隔（預設 6 小時）沒整理過」才會真的重新整理一次 （複製資料進 BigQuery 原生表），其餘時候直接沿用，速度接近 native 模式；每天排程抓完 當天資料後也會自動強制重新整理一次，正常情況下完全不用手動按任何按鈕。

排程佇列

這裡的四種背景工作（重新計算戰報／資料範圍重新彙整／因子迴歸模型／立即重新整理） 都是排時間觸發器在背景執行，不管在哪個分頁、哪台裝置觸發的都看得到目前狀態；卡在 「執行中」太久或變成「錯誤」，可以直接在這裡重新啟動，不用回到各自的頁籤重新操作一次。

疑難排解

「戰報與個股」頁面顯示的內容，就是直接讀 Reports 分頁目前的實際內容——如果按下去 顯示有資料，但戰報頁還是顯示「目前還沒有任何戰報」，代表問題在前端那一段；如果這裡 也是 0 列，代表問題出在「重新計算戰報」寫入這一段。「測試伺服器連線」是最單純的 google.script.run 往返測試，不碰任何試算表/BigQuery；「列出已註冊的觸發器」可以 看有沒有預期外堆積的孤兒觸發器（例如已經不存在的函式名稱、或同一個工作被重複註冊）。

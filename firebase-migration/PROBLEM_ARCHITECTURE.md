# 問題架構準則（Problem Architecture Guideline）

這份文件記錄 2026-11 月的一次「問題重構」練習（Chief Problem Architect
框架：高度／深度／廣度／極限四個命題），以及從中選定、具體化出來的
開發準則。**開發過程中遇到新需求、新 bug、要不要加新因子/新策略，先
回來對照這份文件的第 4、5 節，確認沒有偏離。**

## 1. 為什麼有這份文件

這個專案在新增因子（法人資金流向相關）跟策略（`early_accumulation`、
`composite_accumulation`）的過程中，反覆踩同一類坑：訓練候選因子跟
即時計算支援範圍沒對齊、訓練時的缺值補 0 跟即時計算時的缺值留 null
語意不一致、因子的「有效性」只靠「做出來、丟進 LASSO、套用後跑一次
回測看勝率」這個流程判斷。每次都是症狀出現了才回頭查，查到的也都是
「這一個特定因子」的問題，不是流程本身的問題。

使用者提出「我們要找的到底是什麼」（投入後錢會再流入的公司／即使
下跌錢也會再流入的公司）之後，用「然後呢」「頂尖專家會怎麼做」
「名詞換動詞跨界借法」「10x 壓力測試」四個角度重新拆解了這個專案
真正在做的事，選定**深度命題**當作地基——在因子被包裝成任何策略
之前，先用嚴謹的統計方法驗證它本身有沒有資訊含量。

## 2. 四個命題（完整版，當作武器庫）

### 【高度命題】連續追問「然後呢」
原始任務「做一個資金持續流入的公司篩選工具」往下追問三次「然後呢」，
終點不是「今天一份名單」，而是「一套可被統計驗證、會自我偵測失效的
法人資金流向交易系統，長期風險調整後報酬可被信任」。

### 【深度命題】頂尖專家會怎麼做（已選定，見第 4 節）
量化避險基金做「知情交易偵測」的研究員不會把三大法人淨買超加總成
一個數字就拿去訓練，也不會只靠單一視窗的回測勝率判斷因子有沒有用。
他們會：
- 分法人身份別（外資／投信／自營商）個別檢定，不假設三者訊號品質
  一致（自營商常見避險/造市行為，雜訊比例可能遠高於外資/投信）。
- 用 Information Coefficient（因子值跟未來 N 日報酬的 Spearman 等級
  相關係數）＋ t-stat 顯著性檢定，而不是回測勝率，當作因子篩選的
  第一道關卡。
- 用 walk-forward（多個不重疊時間區段分別驗證）取代單一視窗，確認
  訊號不是只在某一段特別準的僥倖。

### 【廣度命題】名詞換動詞，跨界借法
底層動詞是「在雜訊中辨識出對方頂住壓力仍然堅持的承諾」，不是「掃描
股票清單」。可借用的跨域武器（深度命題驗證通過後的延伸方向，見
第 6 節）：
- 急診檢傷：用**重複量測的趨勢**而非單次快照分流。
- 高頻交易：用**成交量時鐘**而非日曆時鐘分桶，量大的天權重應該更高。
- 敘事結構：承諾的強度是**反覆被測試後仍然選擇同一條路的次數**證明
  的，不是單次宣示的大小。

### 【極限/瘋狂命題】10x 壓力測試
如果要求可信度/研究速度 10x，現在「人工點訓練→人工點套用→人工跑
回測→人工讀 Cloud Shell JSON 貼給 Claude 除錯」的迴圈會整個垮掉；
現有因子幾乎都是同一張歷史價量表切出來的，單一資料源已經被榨乾，
要真的 10x 需要自動化驗證管線＋至少一個全新、正交的資料維度（融資
融券、大戶持股分級、借券餘額）。

## 3. 目前選定：深度命題

> 在新增任何「資金持續流入」因子之前，先建立一套 IC／walk-forward
> 驗證管線，把外資／投信／自營商分開檢定，只留下統計上站得住腳的
> 訊號，取代現在「先做出來、回測一次看勝率」的做法。

## 4. 深度命題 → 可執行的開發準則

這幾條是日常開發中**每次都要對照**的具體規則，不是抽象原則：

- **G1．因子要先過 IC 驗證，才能進策略設計／訓練候選清單。**
  不能先做出來丟進 LASSO、套用後看回測勝率再回頭驗證——那是倒果為
  因。新因子一律先用 `lib/factorValidation.js` 的 `computeIcSeries_`／
  `walkForwardIcReport_` 檢定過，通過才進下一步。
- **G2．判斷因子有沒有用，要同時看三件事**：t-stat 顯著性
  （`summarizeIcSeries_.significant`）、跨區段方向一致性
  （`walkForwardIcReport_.signConsistency`）、樣本數是否足夠
  （`MIN_DAILY_SAMPLE_SIZE_`）。只看「平均 IC 數字好看」不夠——平均值
  可能是正負區段互相抵消湊出來的假象。
- **G3．法人資金流向類因子，預設要分身份別驗證**（外資／投信／
  自營商，見 `lib/flowFactors.js`），不要只做合計版，除非驗證證明
  合計版的 IC 不輸任一單一身份別。
- **G4．任何「訓練時」跟「即時計算時」分開實作的因子，兩邊對缺值的
  處理語意要先確認一致**，不要等部署後才發現——這個 session 踩過兩次
  同一類坑（訓練 COALESCE 成 0、即時計算留 null，兩套邏輯各自合理但
  互相打架）。新增任何需要 BigQuery 訓練 view + JS 即時計算兩邊實作的
  因子，動工前先寫一句話說清楚「查無資料時，這個因子在兩邊分別代表
  什麼」。
- **G5．不能只看單一時間窗口的回測/驗證結果就下結論。** 至少要有
  兩個以上不重疊區段（`walkForwardIcReport_` 的 fold）都支持同一個
  方向，才算「這個因子有訊號」，不是賭一次視窗。

## 5. 偏離警訊 Checklist

開發中卡住、或準備要加新東西時，先自問：

- [ ] 我是不是又在「做出來 → 丟進訓練 → 看回測勝率」，跳過了 IC
      驗證這一關？
- [ ] 我是不是又在靠人工貼 Cloud Shell JSON 給 Claude 讀，而不是用
      已經建好的自動化驗證管線？
- [ ] 這次的法人資金流向因子，有沒有照 G3 拆身份別驗證，還是圖方便
      直接用合計版？
- [ ] 這次「看起來有效」的結論，是不是只看了一個時間窗口/一次回測
      （違反 G5）？
- [ ] 這個因子如果同時有訓練（BigQuery）跟即時計算（JS）兩條路徑，
      兩邊缺值的處理語意對過了嗎（違反 G4 會重演 2026-10-13 那兩次
      坑）？
- [ ] 我是不是又在「小步修補」一個症狀（改個門檻、改個 epsilon），
      而沒有回頭問「這個因子本身到底有沒有資訊含量」這個根本問題？

## 6. 深度驗證通過之後：其他三個命題當延伸方向

深度命題是地基，不是終點。等一批因子真的通過 IC／walk-forward 驗證、
站得住腳之後，照優先順序往外延伸：

1. **廣度**：把驗證通過的因子，用成交量加權（借高頻交易的 volume
   clock）取代現在日曆時鐘式的等權重，並把「連續買超天數」的概念
   延伸成「反覆測試下的堅持次數」（借敘事結構／急診檢傷的趨勢型
   量測，不是單次快照）。
2. **高度**：把驗證通過、站得住腳的因子正式包裝成可切換策略，接進
   `SCREENING_STRATEGIES`，但這次是「因子已經證明有效，才設計進出
   場規則」，不是「規則先訂好，事後才發現因子沒訊號」。
3. **極限**：如果驗證流程本身跑起來順、而且因子確實有效，再考慮要
   不要往自動化驗證管線＋新資料源（融資融券／大戶持股分級／借券
   餘額）投資——這是最大的投入，優先順序排最後，等前面都驗證出
   具體成果再評估值不值得做。
